# SkorX QA, QC and security audit — 28 Sep 2026

Scope: everything built so far in both repos — the Flutter app (this repo) and the platform repo `smit-dev-skorx-frontend` (NestJS API, Next.js web and TMS). The audit ran against a local API on the development database (Postgres, port 5433) with throwaway accounts. It did not touch production or any external system.

## 1. Executive summary

**What was tested**
- A code review of every API controller (about 150 routes in 14 modules). It went deep on authentication, authorization, match scoring, casual-match verification, offline sync, payments, orders, subscriptions and registrations. Community and Looking For were reviewed for ownership checks on every write.
- Runtime attacks against a live API: 79 checks in a new regression script (`backend/scripts/e2e-security-audit.js`). They cover authentication, sessions, admin access, IDOR, mass assignment, score manipulation, replay, race conditions, payments, injection, error leakage and headers.
- The existing suites: Flutter (398 tests plus `flutter analyze`), backend unit tests (338, now 347), and the e2e scripts for casual verification (75 checks), offline sync (29), Community and Looking For.
- Dependency audits (`npm audit` for both Node apps) and a secrets sweep of both repos, including git history for `.env` files.

**What held up well**
- **The scoring engine and anti-fraud gate** passed every manipulation attempt:
  - impossible scores, negative, decimal, huge or string values, and a winner that doesn't match the score;
  - scoring after the match was decided or completed;
  - replayed events and 5 parallel points on one version (exactly one was applied);
  - strangers scoring, reading or confirming a match, and a pending opponent submitting a result;
  - stale confirmation rounds, and cancelling a verified match.
  - A correction of a verified score doesn't change it until every player confirms.
- **Casual verification**: unverified matches never count, and guests block verification. Duplicate unfinished matches with the same players are refused.
- **Payments**: prices are set by the server, a client-sent amount is rejected, and every order has its own access key. Forged signatures are refused. Webhooks are verified with HMAC and processed idempotently. `markPaid` row-locks the order.
- **OTP sign-in**: codes are single use and lock after 5 wrong guesses. Tokens with `alg:none`, a tampered payload, an expired date, or a refresh token presented as an access token are all refused.
- Global auth is opt-out (`@Public()`), and the validation pipe rejects unknown fields. Errors never leaked stack traces or SQL. Helmet headers are present. Tokens on the phone are in Keychain/Keystore, and no secrets are committed in either repo.

**What failed (and is now fixed)**: 13 issues. Three are High:
- anyone could make themselves platform admin;
- any signed-in user could read every tournament's entrant list;
- payments fail open in production if the Razorpay keys are missing.

A P1 bug is also fixed: the public tournament listing returned 500 for every request. All fixes were re-tested; the numbers are in section 9.

**Still open (not fixed here)**: 12 items that need a product decision, a coordinated client change, or work on features that aren't built yet. The main ones:
- entry-fee payment is not wired to Razorpay, so a paid registration can never be confirmed;
- the last slot in a division can be oversold;
- tournament creation doesn't check that a TMS plan was bought;
- a registration can be read publicly by its id;
- a phone number can be looked up to see whether its owner is on SkorX;
- two colluding real accounts can still confirm fake matches.

See sections 5 and 6.

**Not tested** (section 8): real Razorpay, push, SMS and email, realtime, uploads, streaming, booking, iOS and tablets, load and performance, the web app's functional flows, and manual UI QA on a phone.

## 3. Security findings

Severity reflects real impact and how exploitable the issue is today. Nothing that looks like a secret is reproduced here.

| ID | Vulnerability | Severity | Component | Impact | Evidence | Status |
|---|---|---|---|---|---|---|
| SEC-001 | Platform admin takeover by self-registration | **High** | `commerce/commerce.guards.ts`, `auth/register` | Anyone who registers a listed admin email before its owner does gets every order (customer name, email, phone, GSTIN, address), all Pro records, Community moderation and sync metrics | Registered `audit-admin@skorx.test` via `POST /auth/register` → `GET /commerce/admin/orders` returned **200** | **Fixed** |
| SEC-002 | Tournament entrant list readable by any signed-in user (BOLA/IDOR) | **High** (latent) | `registrations.controller.ts` `GET /registrations` | Name, email, phone and payment state of every entrant of any tournament. It was masked only because the endpoint crashed (BUG-001); fixing that bug alone would have exposed it | Code had `// TODO: enforce tenant scoping`. After the pagination fix, a stranger's request returns **403** and the organizer's 200 | **Fixed** |
| SEC-003 | Payments fail open without real Razorpay keys | **High** (config) | `razorpay.gateway.ts`, env validation | Production with missing, placeholder or mistyped keys silently runs Test Mode. Public `/commerce/test-gateway` then signs "successful" payments and `confirmPayment` returns true, so every TMS plan, add-on and SkorX Pro is free | Code review; the dev API runs this way by design | **Fixed**: production refuses to start without a real key pair, the webhook secret, and 32+ character JWT secrets that differ |
| SEC-004 | Refresh-token race and no reuse detection | Medium | `auth.service.ts` `refresh` | One stolen refresh token could be used in parallel to fork several sessions, and replaying a rotated token went unnoticed | 3 parallel refreshes with one token → **200, 200, 200** | **Fixed**: atomic rotation (one winner). Replaying a token rotated more than 60 s ago revokes every session of that user (the grace window avoids signing people out after a lost response) |
| SEC-005 | Result edit skipped authorization for a non-casual match with no tournament | Low | `matches.service.ts` `editResult` | Any signed-in user could rewrite such a match. No current API creates one, so this is defence in depth | Stranger `POST /matches/:id/edit-result` → **201** | **Fixed** (403); the edit also row-locks now |
| SEC-006 | JSON-LD "escape" was a no-op | Medium (latent) | web `components/site/seo.tsx` | `"<"` in JS source *is* `<`, so the escape did nothing. Any page that puts user text (tournament or player name) into JSON-LD would have stored XSS. Today's callers pass static content only | Byte check of the source; `</script>` survived the old escape | **Fixed** (double backslash, verified) |
| SEC-007 | Per-IP rate limits share one bucket behind a proxy | Low | `main.ts` | Behind a load balancer every user shares the proxy's IP, so the OTP limit (5/min) is one bucket for everyone | Code review (no `trust proxy`) | **Fixed**: `TRUST_PROXY` setting |
| SEC-008 | Swagger UI public in production | Low | `main.ts` | Full API map for attackers | Code review | **Fixed**: off in production unless `SWAGGER_ENABLED=true` |
| SEC-009 | Unbounded free text on scoring endpoints | Low | `complete-match.dto.ts`, `edit-match-result.dto.ts` | Up to 1 MB of notes per request stored in audit rows | Code review | **Fixed** (500 / 300 characters; at most 7 games) |
| SEC-010 | `GET /registrations/:id` is public and returns PII | Medium | `registrations.controller.ts` | Anyone with a registration id sees name, email and phone. Ids are cuids (hard to guess) but appear in URLs and e-mails | Code review | **Open**: give registrations an access key like orders; the web confirmation page must send it |
| SEC-011 | Phone-number lookup reveals SkorX membership | Medium (privacy) | `GET /casual-matches/players?q=<10 digits>` | Anyone signed in can check whether a number is on SkorX and see that person's name, city and photo (60 lookups/min per account) | Documented behaviour; partial numbers find nobody (tested) | **Open**: product decision. Options: return only "invite sent", require a mutual connection, or lower the rate |
| SEC-012 | Colluding real accounts can confirm fake casual matches | Medium (business) | verification design | Two real people can inflate each other's record. Fraud signals are recorded (`resultSignals`, same lineup in 7 days) but nothing acts on them | Design review | **Open**: act on the signals (cap verified matches per lineup per day, review queue for anomalies, weight rating by opponent diversity) |
| SEC-013 | TMS plan not enforced when creating a tournament | Medium (business) | `tournaments.service.ts` `create` | Any organization owner can create unlimited tournaments without buying a plan | Code review | **Open**: check `TmsEntitlement` in `create` (a product decision on the free tier comes first) |
| SEC-014 | Access token outlives logout or deletion by up to 15 min | Low | `jwt-access.strategy.ts` | A deleted or signed-out user keeps API access until the token expires | Code review | Open (accepted trade-off; add a `deletedAt` check if accounts get banned) |
| SEC-015 | Coupon limits counted on paid orders only | Low | `orders.service.ts` `couponFor` | Parallel checkouts can exceed `maxRedemptions`. TMS orders never evaluate `perUserLimit` | Code review | Open |
| SEC-016 | Android `allowBackup` defaults to on | Low | `AndroidManifest.xml` | Backups include local match files; restored secure-storage keys fail to decrypt, forcing a sign-in | Code review | Open: set `allowBackup="false"` or add backup rules |
| SEC-017 | `deepmerge-ts` advisory (via Prisma CLI) | Info | backend dev tooling | Reached only while Prisma loads its own config, never with request data. `npm audit fix --force` would downgrade Prisma | `npm audit` | Accepted; recheck on the next Prisma upgrade |
| SEC-018 | SkorX Rating computed on the device | Info | `lib/features/rating/arc_engine.dart` | Fine while the rating is shown only to its owner. Once it feeds rankings or other players' views it must move to the server, or it can be forged | Code review | Open (plan before leaderboards) |

## 7. Database consistency

- **Transactions and locks**: match scoring, results, verification, sync and `markPaid` all row-lock (`SELECT … FOR UPDATE`) inside a transaction. Tested: parallel points give exactly one winner, and a replayed event id adds nothing.
- **Idempotency keys** with unique constraints: `ScoreEvent (matchId, clientEventId)`, `MatchSyncEvent (matchId, clientEventId)`, `Match (createdByUserId, clientRef)`, `Registration.idempotencyKey`, `PaymentWebhookEvent (provider, eventId)`.
- **Race risks still open**: registration capacity (BUG-006); coupon redemption counts (SEC-015); `deleteComment` counter decrement (cosmetic).
- **Missing constraints**: no unique entry per person per division (BUG-007).
- **Migrations**: 7, all additive. The new one is `20260928090000_user_email_verified` (a nullable column, safe for running code).
- **Orphans**: tests clean up after themselves. The schema cascades on match children (games, events, participants).

## 10. Recommended remediation order

1. **Before any production deploy**: set real Razorpay keys, the webhook secret, `TRUST_PROXY`, and 32+ character JWT secrets (the API now refuses to start otherwise). Verify each admin's email with `scripts/verify-admin-email.js`.
2. **BUG-005** entry-fee checkout on the commerce order flow, together with **BUG-006** (capacity hold) and **BUG-007** (one entry per person). All three change the same code.
3. **SEC-010** registration access key, together with the web confirmation page.
4. **SEC-013** enforce TMS plans (decide the free tier first).
5. **SEC-011** phone lookup and **SEC-012** collusion signals (product decisions).
6. **BUG-008** release-build guard for `API_BASE_URL`.
7. **SEC-018** move rating to the server before leaderboards ship.
8. Clean-up: SEC-014/015/016, BUG-010/011/012.
